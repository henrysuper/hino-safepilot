# 油耗預測與發派系統 v1（`hino_safepilot.fuel`）

依 `docs/開發說明書.md` 實作。數字全部由確定性程式與 XGBoost 產生；LLM 只負責把已算好的 JSON 寫成文字（可選，預設用固定範本）。

## 安裝與執行

```powershell
pip install -e ".[dev,fuel]"          # 加 ".[ai]" 才能用 Gemini 生成報告文字
hino-etl --repo-root .                # 前置：Phase 2 ETL -> data/interim
hino-fuel segments                    # 步驟 1：3/5/10 km 路段表 + 檢查點 1 報告
hino-fuel train                       # 步驟 2-7：健康度、對照表、模型選擇與驗證
hino-fuel drivers                     # 虛擬駕駛（此為模擬資料）：名單、行程分配、每人各道路的行為平均
hino-fuel score                       # 第 6 節：測試期行程分數與報告範例
hino-fuel dispatch-demo               # 第 5 節：用 ORS 對示範起訖點做發派預測
hino-fuel predict --origin 121.30,24.99 --destination 120.67,24.15 --vehicle <enabledCode> --driver-type eco --driver-type normal [--live]
hino-fuel backtest --trips 60         # 真實行程回測與派車校正（會呼叫 ORS）
hino-fuel route-overlap               # 回測行程是否照規劃路線開
hino-fuel fences                      # 由真實起訖點建立圍籬與慣用路線
hino-fuel fence-test                  # 圍籬對圍籬測試
hino-fuel build-graph                 # 建立本機路網（ORS 額度用完時的備援）
hino-fuel serve                       # 本機檢驗主控台 http://127.0.0.1:8765
```

外部資料（皆 git-ignored）：

| ORS / TDX 金鑰 | `.env`：`ORS_API_KEY`、`TDX_CLIENT_ID`、`TDX_CLIENT_SECRET` | 只在發派預測時使用 |

產出：`data/processed/fuel/`（路段表、對照表 `artifacts/`、行程分數）、`models/fuel/v1/fuel_model.json` + `model_meta.json`、`reports/fuel/`（檢查點與驗證報告）。

## 設計重點（與說明書不同或補充之處）

| 項目 | 做法 | 原因 |
|---|---|---|
| 路徑描述 | 訓練（GPS 軌跡）與發派（ORS 路線）都先沿路徑每 100 m 取點，再查 OSM 道路、DEM 海拔（平滑 500 m）、500 m 網格 | 兩邊特徵算法一致，避免「訓練用稀疏 GPS、發派用密集路線」造成偏差；道路類型改為依距離多數決 |
| trunk 分類 | `motorroad=yes` 或 `maxspeed>=80` 的 trunk 才算 highway，其餘歸 normal | 台灣 OSM 把很多市區省道標成 trunk |
| `avg_slope` | 段尾減段首海拔 ÷ 路徑長 ×100（有正負號的淨坡度，%）；另有 `elevation_gain_m` 累積爬升 | 上坡與下坡對油耗方向相反 |
| `overspeed_share` | 分母為「行駛中且有速限」的時間 | 怠速不該稀釋超速比例 |
| 行為地圖 | 預估行為 = (車型, 道路類型, 時段) 平均 × 網格因子 × 駕駛類型倍率；網格因子用 w = n/(n+5) 往 1 收縮 | 說明書的加權平均改成乘法形式，可同時處理不同車型經過同一網格 |
| 車輛效率偏差 | 總油耗 ÷ 期望油耗（同車型同道路的總油耗÷總里程），少量資料往 1 收縮；訓練列用「排除當月」的值 | 符合全域原則 3；避免特徵直接含有該段自己的油耗 |
| 駕駛類型倍率 | 每格往該類型的全道路倍率收縮，並強制 very_eco ≤ … ≤ very_aggressive | 原始倍率樣本少時會亂序 |
| 單調限制 | 四項駕駛行為在 XGBoost 設單調遞增 | 歷史資料中「超速多」常代表路況順暢，未加限制時 aggressive 反而被預測較省；加上後驗證 MAPE 只增 0.6 個百分點 |
| 段長 | 3 / 5 / 10 km 都訓練，在訓練期最後一個月（驗證月）比較，3 km 最佳 | 說明書要求「選誤差最小者」；測試期不參與選擇 |
| 排序正確率 | 長度相近（±25%）、實際油耗差 ≥10% 的兩趟行程，模型是否判斷正確 | 歷史中同一趟只跑過一種組合，無法直接觀察反事實 |
| 預測區間 | 驗證月行程「實際/預測」的 10–90 百分位，乘在預測值上 | 簡單、可校準 |
| TDX 對應 ORS | TDX 路段形狀每 20 m 取點建 KD-tree；路線每 100 m 點找 40 m 內最近路段；一段有一半以上點對到才用即時車速（調和平均） | 說明書待確認事項 |
| 分數 | 應有油耗用實際路線、實際時段與**實際塞車程度**，行為填 normal | 塞車不是駕駛的責任 |

## 結果（2025-09 至 11 測試期，行程 ≥ 10 km，275 趟）

| 指標 | 發派模式（行為與塞車用地圖預估） | 事後模式（實際行為與塞車） |
|---|---:|---:|
| 整趟油耗 MAPE | 11.8% | 10.0% |
| 排序正確率 | 89% | 91% |

* 車型別 MAPE（發派模式）：300 系 9.9%、500 系 11.0%、700 系 17.6%。
* 80% 預測區間實際涵蓋 77%。
* 路線切分（藏起 1/5 的 5 km 區塊、連對照表一起重算）：發派模式 MAPE 18.8%，事後模式 15.2%。沒跑過的路比跑過的路誤差大約 7 個百分點。
* 特徵重要度前五：車型、塞車程度、車輛效率偏差、平均坡度、怠速。健康度佔 3%。

## TDX 即時路況（第 5 節，`--live`）

* 使用 `/v2/Road/Traffic/Live/{Freeway,Highway}`（每分鐘更新的 `TravelSpeed`）與 `/v2/Road/Traffic/SectionShape/{Freeway,Highway}`（WKT 路段形狀，快取於 `data/interim/external/tdx/`，30 天更新一次）。國道 465 段、省道 6,832 段。
* 遇到 HTTP 429（頻率限制）自動退避重試；即時車速在記憶體快取 60 秒，同一次發派的多條路線共用一次查詢。
* congestion_index = TDX 車速 ÷ 該段卡車暢通車速，上限 1.0（TDX 是全車種車速，高於卡車暢通車速只代表不塞）。
* 對不到 TDX 的段（多為市區道路）自動改用歷史塞車地圖，每段都會標示 `congestion_source`。
* 示範任務實測（2026-10-03 17:12 出發）：桃園→台中 45 段中 41 段用 TDX；台北→基隆 9 段中 6–8 段；台中→埔里 17–18 段中 14–16 段。

## 真實行程回測（`hino-fuel backtest`，使用者同意將真實起訖點送到 ORS）

流程：真實行程的起點、終點與出發時間 → ORS driving-hgv → `FuelPredictor`（出發時段的歷史塞車地圖、normal 駕駛類型）→ 與整趟實際油耗比較。只用單程型行程（≥10 km 且起訖直線距離 ≥ 行駛距離 30%），依車型分層抽樣。ORS 回應快取在 `data/processed/fuel/backtest_ors_cache.json`，重跑不會再呼叫。

* **校正**只用訓練期另一組 60 趟真實行程：在「不校正 / 加場站開銷 / 乘中位數倍率 / 兩者」中以 leave-one-out MAPE 選擇，油耗與時間各自選；預測區間改用這組行程「實際 ÷ 校正後預測」的 10–90 百分位，納入路線不確定性。結果存於 `artifacts/dispatch_calibration.json`。
* **評估**用測試期 60 趟，校正前後都報告（`reports/fuel/backtest_real_trips.json`）。

主要發現：誤差主要來自「ORS 規劃路線 ≠ 實際行駛路線」（中位長度差約 10%，實際路線常含繞路、多點停靠與場內移動），而不是油耗模型本身：同一批行程若用實際 GPS 軌跡預測，誤差約 15%。

### 司機有沒有照規劃路線開（`hino-fuel route-overlap`）

重疊度 = ORS 路線與實際 GPS 軌跡在 200 m 內的比例（兩個方向取較小者）。測試期 60 趟：

| 分組 | 趟數 | 油耗 MAPE | 實際 ÷ 規劃里程 |
|---|---:|---:|---:|
| 照規劃路線開（≥80%） | 23 | 15.5% | 1.05 |
| 部分照開（50–80%） | 11 | 27.8% | 1.22 |
| 走了別條路（<50%） | 26 | 35.6% | 1.27 |

## 圍籬（`hino-fuel fences`、`hino-fuel fence-test`）

* 主辦方資料的 `fenceId` 全部為空（FAQ Q1），主辦方允許自行假設圍籬。系統用訓練期所有行程的起訖點做 DBSCAN（300 m）自動建立資料圍籬（134 個，涵蓋 71% 的起訖點），前 40 個用 ORS 反向地理編碼取名。圍籬座標是真實場站/客戶位置，只存在 `data/processed/fuel/`。
* **慣用路線**：同一組圍籬之間、訓練期至少 2 趟且里程一致（最長 ÷ 最短 ≤ 1.3，排除多點配送）的行程，取中位里程那趟的 GPS 軌跡當「路線 H」。發派時起訖都在圍籬內就自動加入比較（60 組）。
* **圍籬對圍籬測試**：測試期 59 趟（16 組圍籬，每組只呼叫 1 次 ORS）。整體 MAPE 39%；照規劃路線開的 22 趟 10.7%；排除多點配送後 19.0%；有慣用路線的 38 趟，ORS 路線 23.7% → 慣用路線 13.9%。

## 圍籬任務（多點停靠、指定出發時間）

發派一律以圍籬為單位：起點圍籬 →（0–6 個中途停靠圍籬）→ 終點圍籬。

* **示範圍籬**（`config/fuel_demo_fences.json`，此為模擬資料）：12 個公開物流地點（港口、機場貨運區、工業區、科學園區），半徑為假設值；另附 4 個示範任務。
* **資料圍籬**：由真實行程起訖自動建立（見上節），只存在本機。
* 使用者指定日期與出發時間（或勾「現在出發」改用 TDX 即時路況），中途停靠點可設停留分鐘。系統依序推算每站預計抵達與離開時間，每段的時段特徵用該段的出發時間。不提供「指定抵達時間反推出發」模式。
* 每段的候選路線：ORS（1–3 條）、車隊熟悉路線、慣用路線（兩端都是資料圍籬且有歷史）。每段採用「所有車 × 駕駛組合平均油耗最低」的路線，讓所有組合共用同一份排程。
* 停靠油耗 = 停留時間 × 同車型停靠時引擎未熄火比例（300 系 46%、500 系 59%、700 系 77%）× 怠速油耗率（1.33 / 1.16 / 2.33 L/h），皆由訓練期資料估計。
* ORS 失敗（每日額度用完、斷線）時自動改用本機路網，結果會註明。

## 虛擬駕駛（`hino-fuel drivers`）

資料沒有駕駛身分。與說明書不同（使用者決定）：自建駕駛名單，發派時在同車系內比較「誰開哪台車」最省油，新進駕駛先參考行為相似的資深駕駛。

* **名單**（此為模擬資料）：40 人，300 / 500 / 700 系各 20 / 10 / 10；每人屬於一個車系、平常開其中一台車（每台車 2 人，兩人設定風格相差大）；每車系 1 位新進駕駛，測試期才出車。沒有班表。車牌為模擬車牌（`SIM-3001` 格式，不是真實車牌）。設定在 `config/fuel_v1.json` 的 `drivers`。
* **分配**：每個真實車-日分給同車系的一位駕駛，機率 ∝ exp(−(當天行為排名 − 設定風格)² / 2σ²) × 平常開這台車的加權（自己的車 1、別台 0.3），σ = 0.15；一人一天一台車。行為與油耗仍是真實資料。
* **個人平均**（使用者提出的做法）：駕駛在高速 / 一般道路 / 市區各自的怠速、急加速、急減速、超速，÷ 同樣路段、同時段的一般值（車型×道路×時段先驗 × 500 m 網格因子）。用比值而不是次數，因為次數會受路線影響（常跑塞車市區的人怠速本來就多）。只用「當天以前」的行程。
  * 趟數少：往最相似的 3 位資深駕駛（≥10 趟）收縮，w = 趟數/(趟數+10)；沒有紀錄時用一般值 1.0。
  * 某種道路開得少：往本人的全路段平均收縮，w = 段數/(段數+20)。
* **模型**：油耗模型仍是 v1，用真實路段的實際行為訓練，不看駕駛身分。駕駛只透過「預估行為 = 路段一般值 × 個人平均」影響預測，所以新增駕駛不必重新訓練，只要累積他的行程。曾試過把駕駛倍率當模型輸入（v2）：24 人時 11.6%、40 人時 12.4%，人數一多反而變差，且每次加人都要重訓，已移除。
* **發派**：任務指定車系；該車系每位駕駛 × 每台車都預測，再依油耗由低到高挑組合，每台車、每位駕駛最多出現一次（一台車同時只能一位駕駛開）。第一名為建議派。
* **分數**仍用 v1 的 normal 駕駛類型當基準（說明書第 6 節）。

測試期（≥10 km，275 趟，發派模式）：

| 預測方式 | 整趟 MAPE | 新進駕駛（20 趟） |
|---|---:|---:|
| 不知道是誰開 | 11.8% | 13.2% |
| 用駕駛個人平均 | 11.9% | 13.0% |

* 準確度與不分駕駛相同：駕駛行為對油耗的影響本來就小。700 系示範任務（龜山→臺中港，97% 高速）同一台車換 10 位駕駛只差 34.0–36.0 L。
* 同任務、同車系的差距主要來自車：同一位一般駕駛開 5 台 700 系是 33.8–51.2 L，最耗那台效率偏差 1.17、健康度 66。
* 駕駛排序：每位駕駛「預估個人效應」與「實際效應」的等級相關 0.21，弱相關。
* 派車重播（測試期每趟換成當天沒出車的同車系駕駛，車不變）：模型估計可省 3.6%，屬模型推算，無法實測。
* 限制：分配是依行為設計的情境，駕駛的一致性是模擬出來的，以上結果不能當作真實車隊的證據。

## 本機路網（`hino-fuel build-graph`）

由台灣 OSM 建立的可行車路網（約 480 萬節點、510 萬路段，遵守單行道），Dijkstra 以名目卡車速度計時，免費、無次數限制。另設「車隊熟悉」權重：訓練期車隊跑過的 500 m 網格內的路段成本減半，用來產生「車隊熟悉路線」候選。

## 提升準確度的實驗（測試期同一批 60 趟真實行程）

| 做法 | 整趟油耗 MAPE | 偏差 | 採用 |
|---|---:|---:|---|
| ORS 只給起訖點（原本） | 26.4% | −27% | 基準 |
| 每台車改用近 14/30/60 天效率偏差 | 11.4–12.7%（軌跡模式，原本 11.6%） | | 否：差異在誤差範圍內 |
| ORS 改走免收費道路 | 27.9% | | 否：與實際路線重疊更低（0.45 vs 0.60）；設定 `avoid_toll_candidate` 可開啟 |
| 車隊熟悉路線（只有起訖點） | 28.4% | −30% | 作為候選路線 |
| 加入實際中途停靠點 | 25.3% | −25% | 是（多點任務） |
| 停靠點 + 車隊熟悉路線 | 25.1% | −25% | 是 |
| 停靠點 + 熟悉路線 + 停靠怠速油耗 | **24.1%** | −22% | 是 |
| （參考）司機照規劃路線開 | 15.5% | +6% | |

剩下的誤差主要是規劃之外的繞路（實際里程仍比規劃多 15%）與資料中沒有的載重。

## 本機檢驗主控台（`hino-fuel serve`）

```powershell
hino-fuel serve            # 開啟 http://127.0.0.1:8765
```

* **發派預測**：選示範任務或自行以圍籬設定起點、中途停靠與終點（下拉選單或點地圖圓圈），中途停靠可設停留時間；設定日期與出發時間（或勾 TDX 即時路況、現在出發），按車系按鈕即開始比較。顯示建議派（駕駛、車牌、車系、油耗）與排名表（排名、車牌、系列、駕駛、預測油耗；每台車一位駕駛）。
* **虛擬駕駛**：名單與各道路的個人平均、相似駕駛、準確度比較、新進駕駛學習曲線、派車重播。
* **真實行程回測**：校正前後指標、每趟實際 vs 預測；點選後在地圖畫出 ORS 路線（預設關閉底圖，避免把真實行程範圍送到公開圖磚伺服器）。
* **油耗分數與報告**：測試期每趟分數；點選後即時產生 Gemini 報告，並附固定範本、逐段明細與交給 LLM 的 JSON。
* **模型驗證**：檢查點 3 指標、段長比較、特徵重要度、駕駛類型倍率、健康度與效率偏差。

安全：只綁定 127.0.0.1、沒有登入驗證，是單人本機工具，不可對外開放。瀏覽器只會看到車輛代號（V01…），看不到 enabledCode。Leaflet 由 unpkg CDN 載入（固定版本並有 SRI 檢查）。

## LLM 報告文字

`.env` 有 `GEMINI_API_KEY` 時自動使用 Gemini（`GEMINI_MODEL`，預設 `gemini-3.5-flash-lite`；`LLM_PROVIDER=none` 可關閉）。回覆若含 JSON 以外的數字、英文欄位名稱或超過 220 字就退回固定範本。

## 限制

* 資料沒有載重；700 系誤差最大，推測載重變化是主因。
* 駕駛類型在高速公路路線上的差異很小（0–2%），市區路線較大；倍率來自真實行為，但駕駛名單為模擬資料。
* ORS 的 hgv 行車時間與本系統的預估時間不同：本系統用歷史卡車車速與塞車程度修正。
* 發派預測的準確度取決於任務是否列出所有中途停靠點；未列出的停靠與繞路會讓實際油耗高於預測。
* 主控台詳細說明與後續開發交接：`docs/fuel_console_guide.md`。
